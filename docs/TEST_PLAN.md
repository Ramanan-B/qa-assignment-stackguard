# Test Plan: Sauce Demo Checkout Flow

## 1. Scope

**In scope:** the purchase journey on https://www.saucedemo.com, covering:

1. Login.
2. Product list (add, remove and sort products).
3. Cart.
4. Checkout step one: customer information.
5. Checkout step two: order overview and totals.
6. Order confirmation.
7. Logout.

**Out of scope:**

- **Real payment processing.** The site has none.
- **Performance and load testing.** The site is public and shared, so it must not be load-tested.
- **Security testing beyond access control.** That is limited to checking that pages can't be reached after logout.
- **Accessibility audit.** It would be the next step if there were more time.

**Test accounts.** The site lists them on its login page, and all use the password `secret_sauce`:

| Account | Use |
|---|---|
| `standard_user` | The baseline. Most tests run with it. |
| `locked_out_user` | The negative login test. |
| `problem_user`, `error_user`, `visual_user` | Exploratory testing. These accounts are intentionally faulty and showed real defects (see [BUG_REPORTS.md](BUG_REPORTS.md)). |

**Test data.** Checkout data is generated by each test. The site keeps cart state in the browser's local storage. Each Playwright test runs in a fresh browser context, so tests start with an empty cart and don't affect each other or other users.

## 2. Main risks

| # | Risk | Why it matters | Likelihood |
|---|---|---|---|
| R1 | A customer can't complete a purchase | Lost revenue on the most important journey | Medium. Confirmed for `problem_user` and `error_user`. |
| R2 | The order total is wrong (item total, tax or total) | Customers are over- or under-charged, which causes legal and trust problems | Medium. A rounding defect in the displayed item total was confirmed. |
| R3 | The cart content is wrong: items lost, duplicated, or with the wrong price or quantity | The customer receives or pays for the wrong goods | Medium |
| R4 | Checkout accepts invalid or incomplete orders: an empty cart or missing customer details | Orders that can't be fulfilled reach the business | High. An empty-cart order was confirmed. |
| R5 | Listed prices differ from the prices charged | Misleading pricing and customer complaints | Low. Confirmed for `visual_user`. |
| R6 | The session isn't ended correctly at logout | Another person on a shared device could see or change the account | Low |

## 3. Top 10 test cases (priority order)

Priority is based on business impact first, then on how often a real customer would hit the problem.

| # | Test case | Expected result | Risk | Automate? | Why |
|---|---|---|---|---|---|
| 1 | **Happy-path purchase.** Log in as `standard_user`, add 2 items, open the cart, check out with valid details and finish. | The confirmation page shows "Thank you for your order!" and the cart is empty afterwards. | R1 | **Yes** | This is the core revenue path, so it should be checked on every build. It's stable and deterministic. |
| 2 | **Order totals.** Add several items and open the overview. | The item total equals the sum of the item prices, tax is 8% of the item total rounded to cents, the total is item total plus tax, and every amount has exactly 2 decimal places. | R2 | **Yes** | Exact arithmetic is precise and repetitive, so it is best checked by code. A human can easily miss `$99.94999999999999`. |
| 3 | **Required customer details.** Leave first name, last name and postal code empty, one at a time. | A field-specific error appears and the user stays on step one. | R4 | **Yes** | This is one test run with several data rows, so it is cheap to automate. |
| 4 | **Cart contents match.** Add items, then remove one from the cart page. | The cart badge, the cart list and the overview all show the same items and prices. The removed item is gone everywhere. | R3 | **Yes** | The cart is changed in three places, so it can easily break during changes. |
| 5 | **Empty-cart checkout is blocked.** Open the cart with no items and try to check out. | Checkout is disabled, or an error is shown. No order is confirmed. | R4 | **Yes** | This was confirmed as a bug, so an automated test stops it from coming back unnoticed once fixed. Until then it is marked as a known failure. |
| 6 | **Login.** Try a valid user, `locked_out_user`, a wrong password and empty fields. | The valid user reaches the product list. Each failure shows the correct error and the user stays on the login page. | R1 | **Yes** | Login is the entry point to every journey and the tests are quick and deterministic. |
| 7 | **Logout ends the session.** Log out, then open `/inventory.html` directly and use the browser Back button. | The user is sent to login with an error message, and no protected page is shown. | R6 | **Yes** | This is a security-related check that is easy to break and easy to automate. |
| 8 | **Cancel and back navigation.** Cancel on step one and on step two. | The user returns to the cart or product list and the cart contents are kept. | R3 | **Yes** | These paths are less common but are often broken by routing changes, and they're cheap to automate. |
| 9 | **Purchase with the other test accounts.** Repeat test 1 as `problem_user`, `error_user` and `visual_user`. | The same result as `standard_user`. | R1, R5 | **Manual** (exploratory) | Each account fails differently and on purpose. Exploratory testing finds more here than scripts would. Each confirmed bug then gets one automated check. |
| 10 | **Input edge cases.** Try a postal code with letters or symbols, names that are only spaces, very long values and non-Latin names. | Behaviour follows the field rules, for example the postal code format. | R4 | **Manual** for now | No validation rules are documented, so automated tests would have no defined expected result. Automate once the product owner agrees the rules. |

## 4. Automation approach

- **Tool:** Playwright with TypeScript, Chromium. The UI and API suites are separate Playwright projects.
- **Page Object Model:** one class per page (`LoginPage`, `InventoryPage`, `CartPage`, `CheckoutPage`), so a locator change is fixed in one place.
- **Locators:** the site's `data-test` attributes through `getByTestId`, with `getByRole` where it reads better. No CSS or XPath tied to layout.
- **No fixed waits:** only Playwright's automatic waiting and web-first assertions (`await expect(...)`).
- **Independent tests:** each test gets a fresh browser context and logs in through a fixture. No test relies on another test's state or order.
- **Known bugs:** marked with `test.fail()` and a link to the bug report. The suite stays green, and Playwright reports the test as unexpectedly passing once the bug is fixed.

## 5. Exit criteria

- Automated test cases 1–8 pass on Chromium, apart from documented known bugs.
- Every defect found is written up in [BUG_REPORTS.md](BUG_REPORTS.md) with a severity.
